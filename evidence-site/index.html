Methodology, data and limitations

Each registered scenario and seed ran once, with no reruns and no code changes between runs. Hidden checks that neither engine can see score the result.

Where the data comes from

AutoHeal is evaluated on an internally built, synthetic e-commerce environment. It does not use a downloaded public dataset or real customer or transaction records. Customers are generated (for example customer12@example.com), and orders, payments and queues are produced by a seeded simulation. It is not connected to any production system.

The language models were used only for inference and tool calling. They were not trained or fine-tuned on this data.

Limitations to keep in mind

  • Same authors. Prospective scenarios were written by the team that developed the agent, after inspecting this simulator. They are not independently designed real-world unseen failures.
  • Designer bias. Some detection and decision thresholds were tuned with earlier scenarios in view.
  • Small, correlated samples.
  • No claim of statistical significance.
  • Simulation. The backend, faults and hidden checks are hand-built. Results do not transfer to arbitrary production systems.
  • Latency and cost.
  • Tool failures.
  • Detection gap. Both systems share one detector, which misses backlogs that grow intermittently.

Full method and provenance

How the simulated environment works

The simulation advances in ticks, one step of simulated time, and stores its state in a SQLite database.

Orders and payments
Normal traffic creates 12 orders per tick, with seeded random customers and amounts. A simulated payment gateway responds in 600 to 1,400 ms. If that exceeds the configured timeout the call times out, and the order silently stays unpaid.
Queue and shipping
Paid orders enter a fulfilment queue with a maximum depth. A worker ships a fixed batch per tick. Messages that do not fit go to a dead-letter store.
Customer data and workflows
A sync job copies customer records from a source system a batch at a time. Scheduled workflows share a single lock, and a running workflow that holds it sends heartbeats.
Controlled faults
Each scenario changes the system after a short warm-up: a simulated release changes a setting, records are left inconsistent, a workflow hangs, or misleading log lines are planted. The fault then affects later ticks through the normal pipeline.
Observable evidence
Logs, per-tick metrics, configuration history with who changed what, and the operational tables through a read-only query tool. Scenario definitions and hidden checks are not visible to either recovery engine.
How the two recovery engines are compared
Same detector
Ten deterministic health checks decide whether a recovery starts at all. If they raise nothing, no model is called and neither engine runs.
AI Agent
A language model investigates through tools and chooses repairs. Single-symptom incidents start on a cheaper model. Several symptoms, or a long undecided investigation, move to a stronger one.
Rule-based Playbook
The shared baseline: fixed rules, no language model, no investigation. It uses the same tool protocol, so it goes through the same tools and safety controls and faces the same verification.
Safety controls
A risk policy, limits on actions, steps and waiting, a guard against repeating a repair that makes no progress, and a payment rule that never charges an order with a payment record. Every limit ends in an escalation.
Independent verification
Closing an incident triggers plain code, not model judgement: 16 probe orders go through the real pipeline, then every health check runs again. An incident closes as resolved only if all probes ship and no check fails.
How the evaluation was designed and scored
Prospective Scenario Evaluation
Ten scenario types, defined after the production version was frozen. Two seeded runs each, per system. Seeds come from a fixed hash rule rather than being hand-picked. Possible bias was declared per scenario before any run.
Development & Regression Tests
Five scenario types, some with three runs, that the system was improved against. They show regression safety. They are reported separately and never combined with the prospective results.
Execution rules
One run per registered scenario and seed, with no reruns and no code changes between runs. Both systems start from the same builder and seed.
Scoring
Each run receives one outcome from hidden checks that neither engine can see. The prospective scoring also requires a correct cause, named orders in an escalation, six further healthy ticks after recovery, and no unrelated changes. Unsafe actions attempted and executed are counted separately.
What is stored
Every run keeps its outcome, tool trace, model requests, tokens, cost and latency in two frozen result files, whose checksums are pinned by tests. Tool results were stored cut to characters, so some recorded results are incomplete.
